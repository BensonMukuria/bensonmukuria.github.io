ACID in databases, one everyday example at a time

Atomicity, consistency, isolation and durability: four promises that keep data trustworthy, explained with simple examples.

By Benson Kimani Mukuria · 5 min read

In this note
  1. The four at a glance
  2. Atomicity
  3. Consistency
  4. Isolation
  5. Durability
  6. When ACID is relaxed
  7. Final thoughts

If you work with data, you will sooner or later meet the word ACID. It stands for atomicity, consistency, isolation and durability, and it describes four promises a database makes about transactions. A transaction is a group of changes that belong together, like moving money from one account to another.

These promises are the reason you can pay for something online and trust that the payment, the order and the receipt all agree with each other. They matter to analysts too, because they decide whether the numbers you pull from a database can be trusted at the moment you pull them. Here are the four, one everyday example at a time.

The four at a glance

PropertyThe promiseIn short
AtomicityEvery step of a transaction happens, or none of them do.All or nothing
ConsistencyA transaction never leaves the data breaking the rules the database knows about.Follow the rules
IsolationTransactions running at the same time do not see or disturb each other's unfinished work.Mind your own business
DurabilityOnce a transaction is confirmed, it stays saved, even if the system crashes.Saved means saved

1. Atomicity: all or nothing

A transaction is treated as one unit. If any part fails, the database undoes everything the transaction did so far.

When it works

Booking a flight

Paying for a ticket means two changes: your account is debited and a seat is reserved for you. If the seat cannot be reserved, the debit is rolled back and you keep your money. The confirmation email is normally sent only after the transaction is saved, so a failed email server cannot undo a booking that went through.

When it is missing

A load that stops halfway

You load 100,000 rows into a table and the connection drops at row 70,000. Without atomicity you are left with half a table and no easy way to know which rows made it. With it, the database discards the 70,000 and you simply run the load again.

In SQL, the pattern for moving money between two accounts looks like this:

BEGIN;
UPDATE accounts SET balance = balance - 5000 WHERE id = 1;
UPDATE accounts SET balance = balance + 5000 WHERE id = 2;
COMMIT;   -- if anything fails before this line, ROLLBACK undoes both updates

The exact keywords vary a little between databases. SQL Server, for example, uses BEGIN TRANSACTION.

2. Consistency: follow the rules

The database only accepts changes that keep its data valid. The rules are the ones you build into it: primary keys, foreign keys, NOT NULL, CHECK conditions and so on. A transaction that would break one of them is rejected.

When it works

An order needs a real customer

A foreign key means you cannot create an order for a customer ID that does not exist. A check on the stock column means a sale cannot push the quantity below zero. The bad insert is refused instead of being saved.

When it is missing

Orders that belong to nobody

Without those rules, orders slip in with unknown customers. They show up later as blank rows in a report and as joins that quietly drop data. For an account that does not allow overdrafts, the same gap lets the balance go negative with no warning.

CREATE TABLE accounts (
    id      INT PRIMARY KEY,
    balance DECIMAL(12,2) NOT NULL CHECK (balance >= 0)
);

With this rule in place, any change that would make a balance negative is refused

One thing to keep in mind: the database only protects the rules it has been told about. A rule like "buyers must be 21 or older" is usually checked by the application, unless someone also builds it into the database.

3. Isolation: no interference

When many transactions run at once, each should behave as if it were running alone. Nobody should see half-finished work from someone else.

When it works

One console left, two buyers

An online shop has one PS5 in stock and two people click buy at the same moment. Isolation makes the database handle them one after the other. One gets the console and the other is told it has sold out.

When it is missing

The double-booked hotel room

Two travel agents check the same room at the same time, both see it as free, and both book it. Two guests turn up for one room.

Isolation is not all or nothing. Databases let you choose how strict it is, from loosest to strictest: read uncommitted, read committed, repeatable read and serializable. The stricter levels are safer but slower, because transactions end up waiting for each other. Many databases, including PostgreSQL, SQL Server and Oracle, default to read committed, while MySQL's InnoDB engine defaults to repeatable read.

For analysts this shows up in a practical way. If you run a report while a large data load is still going, the isolation level decides whether you can end up looking at numbers from a half-finished load.

4. Durability: surviving a crash

Once the database tells you a transaction is committed, that change is permanent. A crash or power cut right afterwards must not lose it.

When it works

The crash before the receipt

You confirm an order and the system goes down before the receipt appears. When it restarts, your order is still there, because it was saved before you were told it succeeded.

When it is missing

The lost game save

You play for an hour, the game crashes, and the progress is gone. In a database that means committed sales or payments vanishing after a restart, and a daily total that no longer adds up.

Most databases do this by writing every change to a log on disk before they confirm it, often called a write-ahead log. After a crash, the database replays that log to put everything back as it was.

When ACID is relaxed

Not every system offers all four promises in full. Some NoSQL and large distributed databases trade strict guarantees for speed and the ability to scale, and instead settle for "eventual consistency", where copies of the data agree after a short delay. That is a design choice and not a flaw, but it is worth knowing which kind of system you are reading from before you trust a number to the last decimal.

Final thoughts

ACID is a big part of what makes a database reliable. Atomicity stops half-finished work, consistency keeps the data valid, isolation keeps simultaneous users from tripping over each other, and durability means saved stays saved.

Next time you pay for something online, think of the few lines of work going on behind the scenes to make sure your money, your order and your receipt all agree.
